# gameWE SourceMod plugin - notes for Claude

SourcePawn plugin (`addons/sourcemod/scripting/gamewe.sp`,
`gamewe_messages.sp`, include `gamewe.inc`, translations) based on the
gameME plugin. It writes extra log lines for the gameWE collector
(`LogToGame`), keeps the server's `logaddress` pointing at the collector,
and executes the collector's replies, which arrive as server commands over
RCON (`gamewe_psay`, `gamewe_msay`, `gamewe_browse`, `gamewe_raw_message`,
... plus the `gameme_*` aliases). It has no database access of its own.

Build: `make build` (needs `spcomp` from SourceMod 1.12+, warnings are
errors), `make package`.

Releases: Conventional Commits + semantic-release (`.releaserc.json`). The
GitHub workflow builds every push to `main` (packages as a workflow artifact
only); `feat`/`fix`/breaking commits make semantic-release bump the version
files (`VERSION`, `GAMEWE_PLUGIN_VERSION`), write `CHANGELOG.md`, commit
`chore(release): vX.Y.Z [skip ci]`, tag `vX.Y.Z` and publish the GitHub
release with the packages. There is no tag-triggered workflow.

## Documentation layout (the same in all gameWE repos)

- Root: `README.md` (overview, requirements, quick start, documentation
  table, components, building, license), `CHANGELOG.md` (generated),
  `LICENSE`, `CLAUDE.md`.
- `docs/`: `INSTALLATION.md` (install, update, uninstall, troubleshooting),
  `CONFIG.md` (all settings), `USAGE.md` (commands, pages, operation),
  `INTERFACE.md` (log lines, RCON commands, APIs between the components),
  `DEVELOPMENT.md` (build, tests, CI, releases); repo-specific extras:
  `gameme-CHANGELOG.txt`.
- New documentation goes into the matching file there; no other top-level
  doc files and no per-distribution install guides.

## Security is part of every change (mandatory)

1. **Every change:** before you call a change done, commit it or open a PR,
   run the `security-check` skill on the diff and fix what it finds. Say in
   your answer which checklist points the change touched and the result
   (one or two lines are enough when nothing was found).
2. **Every release, without exception (standing rule from Dennis):**
   releases are made by semantic-release in CI when `feat`, `fix` or
   breaking-change commits reach `main` (version bump, `CHANGELOG.md`, tag
   `vX.Y.Z`, GitHub release). Before pushing such commits to `main`, run
   the `release-security-gate` skill over the whole repo, without asking
   first. Never tag by hand or edit version files / `CHANGELOG.md`; report
   the gate result and ask Dennis for the go before the push.
3. A finding you cannot fix in scope goes into the answer with file:line,
   impact and a proposed fix. Never silence a compiler warning to get green.

## Before every commit (mandatory, standing rule from Dennis)

Run the `pre-commit-checklist` skill before every `git commit`, together
with `security-check`, also for small fixes:

1. Check `README.md` and the files in `docs/` against the change and
   update them in the same commit.
2. Write the commit message as a Conventional Commit (`feat:`, `fix:`,
   `docs:`, ... see the `pre-commit-checklist` skill). `CHANGELOG.md` and
   the version files are generated by semantic-release; never edit them.
3. Check dependencies and toolchain for updates and *suggest* available
   updates (do not update on your own).
4. Check the licenses of third-party code and keep the license list
   complete and current.

Report the result of each step in one line in your answer.

## Invariants that must not break

- Collector commands are `RegServerCmd` only (server console / RCON),
  never `RegConsoleCmd` or reachable by players.
- Player-controlled text (name, chat, clan tag) goes into log lines only
  through `%L`, exactly as the engine logs it. `%L` does not escape `"`,
  so the collector's parser is the defense against faked events; do not add
  new free-text fields from players to log lines (they would need `"`
  removed first).
- Player chat triggers (`rank`, `top10`, ...) are only read and forwarded;
  the plugin never executes text from chat with `ServerCommand`.
- `ServerCommand` only with fixed command names; values from cvars or
  command arguments must not contain `;`, `"` or newlines.
- Buffers: every `Format`/`strcopy`/`GetCmdArg` uses the real buffer size;
  user ids from commands are resolved with `GetClientOfUserId` and checked
  with `IsClientInGame` before use.
- New code that opens URLs (`gamewe_browse`, MOTD) accepts only
  `http(s)://`.
